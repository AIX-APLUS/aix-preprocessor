# Ubuntu 파일럿의 행 검증과 학습 데이터 품질

2026년 11월 19일 UTC에 실행한 다섯 파일럿에서 380행을 생성했다. 양성은 54행(14.21%), 음성은 326행이다. 1행은 같은 병합에서 양쪽 부모가 모두 변경한 Java 기준 파일 한 개다. 양성은 고정 Git 버전으로 부모를 다시 병합했을 때 해당 경로에 텍스트 내용 충돌이 발생했다는 뜻이다. 사람이 실제로 어떤 해결 방법을 사용했는지, 의미적 충돌·빌드 오류가 있었는지는 이 레이블로 알 수 없다. [원본 품질 집계](../../research/repository-audit/evidence/runs/quality.json) · [병합 판정 코드](https://github.com/AIX-APLUS/aix-preprocessor/blob/06e755ebabed1707a3413ec99ffa2511b046c543/src/main/java/io/aix/preprocessor/MergeAnalyzer.java)

수정 후 Ubuntu 실행에서도 380행과 다섯 논리 해시, 분할 267/57/56이 일치했다. 이 보고서에 인용한 실행 시간과 자원 사용량은 최초 실행에서 측정했다. [재실행 결과와 품질 JSON 비교](final-ci-validation.md)

## 어떤 이력을 실제로 추출했나

아래의 기본 브랜치 수치는 고정 SHA까지의 모든 도달 가능 커밋이다. 공개 heads·tags 전체는 별도로 보존한 refs 목록 기준이다. 파일럿에서는 고정 SHA에서 첫 부모를 역추적해 초기의 두 부모 병합 이정표를 선택했다. 새 bare 저장소의 유일한 ref `refs/heads/pilot`이 그 SHA를 가리키는지 검사한 뒤 해당 조상을 모두 추출했다. 다섯 anchor의 GitHub Compare에서도 `behind_by=0`을 확인했다. 고정 SHA 쪽의 추가 커밋 수와 파일럿 커밋 수의 합이 고정 기본 브랜치 이력과 모두 일치했다. JabRef에서는 그래프 수집 당시 기본 브랜치가 앞으로 이동했으므로 함께 보관한 실시간 heads·tags 수치와 고정 SHA 수치를 구분한다. [고정 SHA 목록](../../research/repository-audit/pins.tsv) · [독립적인 조상 관계 확인](../../research/repository-audit/evidence/validation/anchor-ancestry.json)

Ubuntu 24.04 runner, Git 2.56.1, Temurin 17.0.21, Python 3.12.3, 논리 CPU 4개, Java 힙 상한 2 GiB, 작업 스레드 2개에서 한 번씩 실행했다. 초는 Java `extract` 시작부터 종료까지의 경과 시간이다. 원격 fetch, stats, 별도 검증, 토큰화와 분할 시간은 제외했다. RSS는 GNU time의 `%M`으로 얻은 명령 실행 중 최대 상주 메모리이며 runner 전체 또는 동시 프로세스 메모리 합계는 미측정이다. 데이터 크기는 생성된 개별 Parquet 바이트다. 위 효율은 각 파일럿 내의 관측값이며 전체 추출 시간이나 병렬화 효과를 추정하기에는 범위와 반복 측정이 부족하다. ### 어떤 단계에서 병합이 제외됐나

첫 부모와 둘째 부모 순서는 원래 Git 순서다. ‘양쪽 겹침 없음’은 첫 부모에 Java 수정이 있었지만 둘째 부모와 공통 경로가 없던 수다. 마지막 두 열의 단위는 각각 병합, 파일이다. 한 병합이 여러 파일을 낼 수 있다.

| 저장소 | base 0개 / 복수 | 부모가 base와 같음 | 첫 부모에 Java 수정 없음 | 양쪽 겹침 없음 | 겹침이 있는 병합 | 양쪽 수정 Java 파일 발생 수 |
|---|---:|---:|---:|---:|---:|---:|
| Spring Boot | 0 / 0 | 55 | 0 | 36 | 10 | 27 |
| Jenkins | 1 / 9 | 13 | 41 | 105 | 44 | 148 |
| Card Forge | 0 / 0 | 0 | 0 | 1 | 1 | 1 |
| JabRef | 1 / 1 | 49 | 48 | 86 | 49 | 195 |
| Quarkus | 1 / 0 | 41 | 7 | 46 | 6 | 9 |

이번 다섯 범위에서는 Java 양쪽 수정 파일 발생 수와 최종 행 수가 각각 일치했다. 경로 후보 판정 뒤 비텍스트 충돌, 소스 디코딩, 이력 조회 등으로 추가 제외된 파일은 0개였다. Squash·rebase로 생성된 단일 부모 커밋은 첫 단계부터 두 부모 병합으로 관측할 수 없다. [저장소별 funnel 및 skipped 집계](../../research/repository-audit/evidence/runs/)

## 라벨과 15개 컬럼을 어디까지 검증했나

- 모든 실행에서 refs·추출기 SHA·정상 종료를 확인했다. 추출기 stderr의 최종 집계, 별도 `stats` 출력, Parquet 독자의 전체 행 집계, 전체 파일을 다시 읽은 품질 보고서의 행·양성·음성 값이 일치했다. 15개 컬럼의 필드 순서·이름·자료형을 footer에서 검사하고 `(repo_id, merge_sha, base_path)` 중복 키를 거부했다. 저장소별 전체 논리 행 SHA-256도 보존했다. [독립 Parquet 독자](../../benchmarks/DumpParquet.java) · [논리 행 검사](../../benchmarks/dataset.py) · [재검산 스크립트](../../research/repository-audit/verify_results.py)
- 잘못된 스키마 및 중복 입력을 주는 대조군은 두 경우 모두 결과 파일 없이 거부됐다. 원본 다섯 파일을 합친 결과와 각 파일의 행 순서·전 필드가 같았고, 합친 뒤 분할한 결과와 개별 분할 후 같은 파티션끼리 합친 결과도 키와 전 필드가 일치했다. [집계](../../research/repository-audit/evidence/runs/quality.json)
- 원본 Artifact에는 측정 JSON이 담겼다. Ubuntu에서 원본 Parquet 전 행을 읽었고, 보존된 집계들은 로컬에서 다시 대조했다. 후속 재추출은 같은 anchor에서 새로 생성한 행의 SHA-256을 Ubuntu 논리 해시와 비교한다. Golden 비교기의 고정 fixture 데이터 검사 5건도 로컬에서 통과했다. 이 5건은 비교기 자체의 단위 검사다. 실제 외부 프로젝트의 레이블을 사람이 독립적으로 재판정한 정확도는 미측정이다. [Golden 비교기 단위 검사](../../benchmarks/test_dataset.py)

## 모델 입력 길이와 다양성

실제 `Qwen/Qwen2.5-Coder-0.5B`의 tokenizer.json 리비전은 `8123ea2e9354afb7ffcc6c8641d1b2f5ecf18301`, 파일 SHA-256은 `c0382117ea329cdf097041132f6d735924b697924d6f6fc3945713e96ce87539`이다. 워크플로가 지정한 라이브러리는 `tokenizers==0.21.4`다. base 코드에 특수 토큰을 추가하거나 자르지 않고 계산했다. Git 특성, 프롬프트, 레이블에 사용할 토큰은 추가로 예산을 잡아야 한다. 분위수는 행 가중 nearest rank다. Ubuntu 원본의 분위수만으로 좁힌 범위는 전체 380행 중 4,096토큰 초과 115~190행(30.26~50.00%), 8,192토큰 초과 39~172행이다. 예를 들어 JabRef의 98번째로 짧은 파일이 4,134토큰이므로 적어도 98개 파일 발생이 4,096토큰을 넘는다. 32,768토큰을 넘는 행은 다른 저장소의 최대값까지 확인해 Forge 1개(0.26%)로 확정할 수 있다. 프롬프트를 포함한 최종 입력 길이나 실제 학습 시 적용된 절단율은 이 수치로 측정할 수 없다. [분위수에서 재계산한 경계](../../research/repository-audit/evidence/validation/pilot-integrity.json)

JabRef와 Jenkins가 전체 380행 중 343행(90.26%), 양성 54행 중 47행(87.04%)을 제공한다. 전체 고유 경로는 저장소와 경로를 묶어 셌다. 54개 경로가 여러 번 등장했고 여기에 172행이 속했다. 정확히 같은 base 코드가 다른 레이블로 나타난 그룹은 2개(4행)다. 충돌은 부모 양쪽의 변경에 좌우되므로 같은 base 코드만 보고 모든 레이블을 결정할 수 없다. 구문·기능 다양성과 프로젝트 전체의 스타일 다양성은 경로 수만으로 측정하기 어렵다. [원본 프로젝트별 모듈·반복·코드 통계](../../research/repository-audit/evidence/runs/quality.json)

위 표의 유효 행을 낸 병합 110개에는 음성만 낸 병합도 들어간다. 원래 Ubuntu 집계로는 양성이 0행인 두 저장소에서만 고유 양성 병합 수를 확정할 수 있었다. 6개 Git 이력 특성도 15개 필드 검사에 포함됐으나 그 분포는 원본에 없었다. 추가 측정은 이 구분을 유지하며 같은 데이터를 재현한 범위에서 해석한다. [15컬럼 정의](../../benchmarks/dataset.py)

### 같은 논리 행을 재현해 추가로 측정한 값

같은 과거 anchor에서 2스레드로 추출을 다시 실행했다. 쿼리 대상은 보존된 단일 ref의 완전한 조상 이력이다. 로컬 실행은 복제 단계가 실패하던 Windows CLI 래퍼를 건너뛰고 기존 추출 코드와 Parquet writer를 호출했다. 다섯 파일 모두 필드 15개 전체를 사용하는 키 정렬 논리 SHA-256, 행 수·양성 수·음성 수가 Ubuntu와 동일했다. 같은 리비전·해시의 토크나이저로 얻은 저장소별 토큰 분위수도 원본과 일치했다. 아래 값은 그 동일성 검사를 통과한 파일을 추가로 읽어 측정했다. 성능 표의 시간·RSS는 Ubuntu 측정값이다. ### 세 입력 방식의 공정한 비교

먼저 같은 행 ID, 레이블, 시간 경계와 외부 평가 저장소를 고정한다. 코드만, 코드+이력, 이력만 쓰는 세 모델에 같은 행과 분할을 준다. 입력 예산·절단 규칙을 기록하고, 길이 때문에 제외하는 행이 있으면 세 조건에서 공통 평가 행을 사용한다. 각 조건에서 실제 프롬프트 토큰 수와 잘림 전후의 양성·음성 수를 남긴다.

경로 단위 분할은 같은 파일을 외운 효과를 줄인다. 병합 단위 분할은 같은 개발 작업을 함께 보존하지만 같은 파일이 시기를 달리해 양쪽에 남을 수 있다. 두 기준의 연결 요소가 지나치게 커지면 경계 그룹을 제외한 행 수도 보고한다. 시간 평가에서는 병합 시각을 기준으로 훈련→검증→테스트 경계를 선고정하고 경계를 가로지르는 그룹을 격리한다. 독립 저장소 평가는 튜닝 전에 보류한 저장소 전체를 사용한다. 고유 양성 병합 수, 병합 단위 불확실성과 양성 정밀도·재현율을 각 평가에서 따로 보고한다.
